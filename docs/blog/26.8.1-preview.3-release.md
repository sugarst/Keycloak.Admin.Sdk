# Keycloak.Admin.Sdk 26.8.1-preview.3 发布：从管理 API 到应用协议的 .NET 10 SDK

Keycloak.Admin.Sdk **26.8.1-preview.3 已发布到 NuGet**。

这个版本围绕固定的 **Keycloak 26.8.1**，把管理 API、应用认证与授权协议、ASP.NET Core 宿主集成，以及统一功能开关整理为四个可按需引用的包。主包和协议包保留 Native AOT 支持，宿主集成与平台开关包面向 Managed 应用。

如果你正在用 .NET 接入 Keycloak，希望减少手写 HTTP、令牌处理和协议胶水代码，可以从这个版本开始了解项目。

- 项目地址：[sugarst/Keycloak.Admin.Sdk](https://github.com/sugarst/Keycloak.Admin.Sdk)
- 本次工程整理所在分支：[codex/keycloak-26.8.1-full-coverage](https://github.com/sugarst/Keycloak.Admin.Sdk/tree/codex/keycloak-26.8.1-full-coverage)
- 运行平台：**.NET 10**
- 目标服务端：**Keycloak 26.8.1**
- 开源协议：**Apache-2.0**

## 一、项目解决什么问题？

在 .NET 项目中接入 Keycloak，往往包含两类工作。

一类是管理操作：创建用户、维护组和角色、配置客户端、管理认证流程、组织及授权策略。另一类是应用协议：OIDC 登录、令牌刷新、Token Exchange、账户管理、资源授权，或者 SAML、SCIM 和钱包凭证流程。

这些需求共享身份平台，却有不同的调用身份、协议约束和生命周期。管理服务账号的 token，不能直接当作普通用户的协议凭据；一个 HTTP 请求返回成功，也不能说明浏览器登录、防重放或者用户授权已经处理完整。

Keycloak.Admin.Sdk 将这些职责分开，在类型化客户端之外提供能力检查、协议状态处理、宿主集成和独立的验证工具。业务项目可以按需选择模块，同时保留对 HTTP、凭据、会话和配置生命周期的控制。

## 二、四个 NuGet 包，按场景选择

| NuGet 包 | 主要用途 | Native AOT |
| --- | --- | --- |
| `Keycloak.Admin.Sdk` | Admin REST API、服务账号认证、DI、响应处理和支持策略 | 支持，已验证 Linux `linux-musl-x64` |
| `Keycloak.Admin.Sdk.Protocols` | OIDC/OAuth、账户、SCIM、授权、钱包和身份代理等应用协议 | 支持，按能力及 RID 验证 |
| `Keycloak.Admin.Sdk.Hosting` | ASP.NET Core 登录、JWT 资源服务器、注销、MCP 资源元数据和 SAML SP | 仅 Managed |
| `Keycloak.Admin.Sdk.Platform` | Admin 与协议链的统一宿主开关、微软功能管理及可选 Application Insights | 仅 Managed |

依赖关系保持清晰：

```text
Keycloak.Admin.Sdk
└── Keycloak.Admin.Sdk.Protocols
    ├── Keycloak.Admin.Sdk.Hosting
    └── Keycloak.Admin.Sdk.Platform
```

上图表示下层包引用上层包。只做管理 API 调用时，引用主包即可；引用 Protocols 会带入主包；Hosting 和 Platform 分别引用 Protocols，二者互不依赖。需要 Web 宿主集成和统一开关时，可以同时使用 Hosting 与 Platform。

### 安装指定版本

按实际需要执行相应命令，无需为简单场景安装全部四个包：

```shell
dotnet add package Keycloak.Admin.Sdk --version 26.8.1-preview.3
dotnet add package Keycloak.Admin.Sdk.Protocols --version 26.8.1-preview.3
dotnet add package Keycloak.Admin.Sdk.Hosting --version 26.8.1-preview.3
dotnet add package Keycloak.Admin.Sdk.Platform --version 26.8.1-preview.3
```

四个包采用相同版本号，建议保持一致。

NuGet 页面：[主包](https://www.nuget.org/packages/Keycloak.Admin.Sdk/26.8.1-preview.3)、[Protocols](https://www.nuget.org/packages/Keycloak.Admin.Sdk.Protocols/26.8.1-preview.3)、[Hosting](https://www.nuget.org/packages/Keycloak.Admin.Sdk.Hosting/26.8.1-preview.3)、[Platform](https://www.nuget.org/packages/Keycloak.Admin.Sdk.Platform/26.8.1-preview.3)。

## 三、preview.3 更新了什么？

### 1. 管理 API：保持 520 项生成契约，扩展支持与验证范围

主包根据固定 Keycloak 源码和 OpenAPI 生成 **520 项 Admin API 操作**，包括用户、组、角色、客户端、作用域、身份提供方、认证流程、组织、工作流及管理控制台扩展等。

这一版本的重点包括：

- SSF 的 19 个 Admin 操作完成独立支持晋升。
- OID4VC 的 7 个 Admin 操作完成独立支持晋升。
- Client Types 的 2 个操作补齐 Native AOT 独立验证。
- 当前目录共 506 项 Supported，另有 14 项保留为 FGAP v1 Compatibility。

520 是生成契约总数，506 是支持目录中的 Supported 数量。默认正式路线、兼容路线及非 Stable 功能有各自的验证范围，不能把这些数字相加。

尤其需要说明：SSF、OID4VC 和 Client Types 仍保留上游的 Experimental 或 Preview 阶段。通过验收不会把它们自动变成 Stable，也不会自动打开服务端或宿主开关。

### 2. Protocols：补齐应用认证与授权流程

新增的 Protocols 包将应用协议与 Admin API 分开维护，主要覆盖：

- **OIDC/OAuth**：发现、JWKS、UserInfo、PKCE 登录事务、ID/access token 验证、刷新及注销。
- **高级授权**：Device、CIBA、PAR、JAR/JARM、标准及旧版令牌交换、委托、JWT Grant、资源指示器和参数化 scope。
- **客户端与令牌安全**：客户端断言、mTLS、DPoP、联合工作负载与 SPIFFE 认证适配。
- **应用接口**：账户、动态注册、SCIM、UMA、AuthZen、Client Admin v2、运行时 OpenAPI、Docker Registry、身份代理与 SSF。

协议调用要求明确提供用户令牌或客户端认证，不会隐式继承管理员身份。签名、issuer、audience、时效、nonce、防重放和用户同意等约束，也按对应流程处理和验证。

### 3. 钱包与认证能力扩展

钱包相关实现覆盖 JWT VC、SD-JWT、mdoc、凭证签发证明、加密签发、Offer/二维码、预授权、刷新与撤销、OID4VP 出示和客户端 attestation。

认证侧补充 WebAuthn、Passkey、恢复码、邮箱确认、Kerberos、临时用户及明确控制的旧版兼容入口。

这些能力都有具体责任边界。例如，SDK 提供协议适配和验证，钱包私钥、安全存储、浏览器认证器、KDC 以及外部工作负载基础设施仍由对应宿主或环境管理。

### 4. Hosting：让协议落到实际 Web 应用

Hosting 面向 Managed ASP.NET Core 应用，提供：

- OIDC Web 登录和 JWT 资源令牌认证。
- 服务端票据及浏览器会话集成。
- 前通道与后通道注销。
- MCP 受保护资源元数据。
- SAML SP，包括 POST/Redirect、Artifact/ECP、签名及加密断言、单点注销等。

模块使用 ASP.NET Core OIDC/JWT 和 ITfoxtec SAML 等组件，要求 .NET/ASP.NET Core **10.0.14 或更新的 10.0 补丁版本**。证书、票据存储、代理信任和多实例会话撤销由宿主配置。

### 5. Platform：统一开关与官方可选遥测

preview.3 将原来的独立 `Keycloak.Admin.Sdk.FeatureManagement` 包整合为 `Keycloak.Admin.Sdk.Platform`，提供统一的 Admin 与协议宿主开关入口。这是本次升级中需要关注的包结构变化。

平台目录包含 **66 项宿主开关**，两个总闸分别是：

```text
KeycloakSdk.AdminApi
KeycloakSdk.Protocols
```

宿主可以选择完整布尔快照，通过原子替换刷新开关；也可以使用 `Microsoft.FeatureManagement` 的动态配置、过滤器和作用域快照。两种模式共用同一个能力检查边界：开关只能进一步收紧已经允许的请求。

Application Insights 使用微软官方发布器，并直接集成在 Platform 包内，不再新增独立遥测扩展包：

```csharp
builder.Services.AddFeatureManagement()
    .AddKeycloakApplicationInsightsTelemetry(enabled: true);
```

这是接入片段，需要引入 `Microsoft.FeatureManagement` 与 `Keycloak.Admin.Sdk.Platform` 命名空间。宿主还须注册 `TelemetryClient`、启动 hosted services，并对相应 feature 设置：

```json
{
  "telemetry": {
    "enabled": true
  }
}
```

**遥测默认关闭**。NuGet 依赖会随 Platform 安装，运行时是否启用由宿主决定。启用后由官方组件产生 `FeatureEvaluation` 事件，缓冲、发送和刷新交给 SDK/channel。该接入不会自动注册请求或依赖追踪。

使用微软引擎与遥测时选择 `KeycloakPlatformOptions.FeatureManager`；原有 `Flags` 快照模式不会触发微软评估事件。普通 manager 与作用域 snapshot 的一致性语义不同，应按宿主生命周期选择。

Platform **不声明 Native AOT 支持，即使关闭遥测也不作该承诺**。需要 Native AOT 的应用可以继续使用主包与 Protocols，并通过主包的 `KeycloakFeatureSnapshotGate` 控制请求。

`contracts` 目录是这一结构的重要部分。它不仅保存接口定义，还记录固定服务端版本、上游阶段、SDK 实现状态、验证计划和运行环境证据。

生成器负责建立客户端契约；独立源码审计、单元测试和真实业务流程分别检查不同问题。支持状态由对应的验证流程晋升，不能仅因为“生成了一个方法”就宣称支持整个功能。

解决方案按 Unit、Integration、PackageConsumption 分组，共 13 个工程；四个生产包数量不变。核心单元测试已解除对真实验收程序的引用，通用工具基础设施集中到 `tools/Shared`。

## 五、快速开始：读取用户列表

下面以已有管理员访问令牌为例，使用带支持策略的客户端读取用户。令牌需要具有读取 serverinfo 及目标管理接口的权限。

```csharp
using Keycloak.Admin.Sdk;
using Keycloak.Admin.Sdk.Capabilities;

using var cancellation = new CancellationTokenSource(TimeSpan.FromSeconds(30));
var ct = cancellation.Token;
var server = new Uri("https://keycloak.example.com/");
using var http = new HttpClient(new SocketsHttpHandler
{
    AllowAutoRedirect = false
});

var tokens = new StaticAccessTokenProvider(
    Environment.GetEnvironmentVariable("KEYCLOAK_ACCESS_TOKEN")
    ?? throw new InvalidOperationException("请设置 KEYCLOAK_ACCESS_TOKEN"));

var support = new KeycloakSupportConfiguration(
    KeycloakTarget.Version,
    KeycloakRuntimeProfile.Managed);

IKeycloakAdminClient sdk = await KeycloakSupportedClient.CreateAsync(
    http, server, tokens, support, cancellationToken: ct);

var response = await sdk.Users.GetUsersAsync(
    "target-realm", first: 0, max: 20, cancellationToken: ct);

foreach (var user in response.Body ?? [])
    Console.WriteLine(user.Username);
```

长期运行的服务可以使用 `ClientCredentialsTokenProvider` 管理服务账号认证，也可以通过 `AddKeycloakAdminSdk` 接入 DI 和 `HttpClientFactory`。

这里有一个值得保留的区别：直接构造客户端或使用默认 DI 注册提供底层调用能力；`KeycloakSupportedClient.CreateAsync` 会读取服务器能力，并在后续请求前执行版本、功能阶段、FGAP 路线、服务端特性和支持证据检查。业务项目应明确选择所需策略。

## 七、从源码构建 NuGet 包

仓库固定使用 **.NET SDK 10.0.403**。四个库项目都可以打包，测试项目和生成器不作为 SDK 包发布。

一般开发验证可以使用：

```shell
dotnet run --file tools/Verify.cs -- --skip-native-publish
```

需要同时验证 Linux Native AOT 时，使用 Docker 入口：

```shell
dotnet run --file tools/Verify.cs -- --native-container
```

`Verify.cs` 会执行构建、生成一致性、单测、覆盖率、四包打包及依赖检查。它也会核对当前矩阵；修改实现后，旧业务证据失效时需要先按仓库流程重新验收和晋升。

如果只想查看打包产物，可以执行以下开发构建：

```shell
dotnet build Keycloak.Admin.Sdk.slnx -c Release
dotnet pack src/Keycloak.Admin.Sdk -c Release --no-build -o artifacts/packages/26.8.1-preview.3
dotnet pack src/Keycloak.Admin.Sdk.Protocols -c Release --no-build -o artifacts/packages/26.8.1-preview.3
dotnet pack src/Keycloak.Admin.Sdk.Hosting -c Release --no-build -o artifacts/packages/26.8.1-preview.3
dotnet pack src/Keycloak.Admin.Sdk.Platform -c Release --no-build -o artifacts/packages/26.8.1-preview.3
```

单独 `dotnet pack` 生成文件不等于完整验收通过。发布候选流程使用：

```shell
dotnet run --file tools/Release.cs
```

该命令要求当前能力矩阵及相关证据有效，并执行完整门禁、真实业务和受保护复验，生成四个包、哈希、来源与验收摘要。它只生成本地候选，包上传由维护者单独执行。`--bootstrap` 用于需要重新建立基础验收证据的流程，不会绕过最终受保护复验。

本次发布前还修复了一个原生构建问题：Docker 上下文遗漏了解决方案根标记，使协议开关生成器无法定位仓库。修复后已重新完成原生构建和真实协议验收。

## 八、升级与使用边界

从 preview.2 升级时，原来引用独立 `Keycloak.Admin.Sdk.FeatureManagement` 包的项目需要迁移至 Platform。可以继续使用布尔快照，也可以接入微软引擎；启用遥测时按官方 publisher 和逐开关配置完成注册。

本版本仍处于 Preview 阶段，公开 API 可能继续调整。版本号前缀与目标 Keycloak 对齐，并不意味着自动兼容其他 Keycloak 版本。服务端部署、数据库运维、集群、控制台及任意第三方扩展也不属于 SDK 包的实施范围。

实际使用时，还应注意：

- 服务账号管理认证与普通用户协议身份分开管理。
- Preview、Experimental 和 Deprecated 能力保持显式许可及对应服务端功能要求。
- HTTP 弹性策略默认关闭；开启后针对适用读取请求，不为写操作和 token POST 自动重试。
- Native AOT 应选择具有对应运行模式和 RID 验证证据的支持配置。
- 只有完整布尔快照模式保证同代读取；微软引擎的请求一致性按宿主选择的作用域 snapshot 管理。
